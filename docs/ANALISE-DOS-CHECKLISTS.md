### 1.2 Campos que existem em todos os checklists (estrutura comum)

1. **Texto de orientação** (igual em todos): "Porque realizar o CKL? Para evitar a contaminação cruzada entre diferentes
   cultivares e garantir a pureza das sementes. Caso o item esteja NC? Deve-se avaliar visualmente as condiçoes de higiene
   do secador. Os resultados serão expressos como conforme "C" ou não conforme "NC". Caso apresente NC solicitar limpeza e
   em seguida reavaliar. Relatar neste documento os comentários relevantes no campo "Observação". As não conformidades devem
   ser relatadas neste documento juntamente com o nome do responsável pelo plano de ação e data prevista."
2. **Informações relevantes**: Cultivar anterior · Próxima cultivar.
3. **Avaliação, por item**: C · NC · Data/Hora.
4. **Reavaliação (em caso de NC no item), por item**: C · NC · Data/Hora.
5. **Regra da reavaliação**: "O campo "Reavaliação" deve ser preenchido somente quando o equipamento estiver conforme, e após,
   deverá selecionar em qual reavaliação a máquina foi liberada." → **Reavaliação: 1° ( ) 2° ( ) 3° ( )**.
6. **Assinaturas**: Responsável pela vistoria · Operador do ponto.
7. **Observações** (texto livre).
8. **Plano de ação em caso de não conformidade** (na própria aba e na aba "Verso"): Data de aplicação do Check List ·
   Descrição da NC · O que será feito? · Como? · Data prevista de conclusão · Quem?

**Só nas UBS**: "TERMO DE CONCLUSÃO DA INSPEÇÃO — O setor de Qualidade realizou a verificação e atesta que a UBS foi
INSPECIONADA e encontra-se ( ) Liberada ( ) Não Liberada para os processos subsequentes."

**Não existe** nos originais a opção "Não se aplica" — só C e NC.

## ETAPA 2 — Estrutura proposta

### 2.1 Duas telas, um sistema (mesmo padrão do app de Fotos TSI)

- **Aplicativo do celular** (`index.html`) — para quem faz a vistoria: entrar com usuário → escolher área (UBS ou
  Secador) → escolher o checklist → informar cultivar anterior e próxima → marcar C/NC item por item (data/hora
  automática) → foto e observação quando NC → reavaliação → assinaturas/termo → enviar. Botões grandes, funciona sem
  internet (guarda no aparelho e envia quando a conexão voltar).
- **Visão desktop** (`painel.html`) — para Qualidade/administração: painel de acompanhamento (previstos, iniciados,
  concluídos, pendentes, com NC, % de conclusão), filtros (período, área, checklist, equipamento, colaborador, status),
  histórico, relatório individual em PDF, exportação Excel, não conformidades e planos de ação em aberto, cadastro de
  modelos/itens/usuários.

### 2.2 Como os dados ficam guardados

- **Modelo de checklist (versionado)**: área, nome, identificação CKL, versão, elaborado/revisado/aprovado por, data de
  aprovação, se tem termo de conclusão, lista de itens (ordem, seção, texto exato, código quando houver, ativo/inativo).
  Alterar um modelo cria uma nova versão; as anteriores ficam guardadas.
- **Execução (um checklist preenchido)**: cópia congelada do modelo usado, cultivar anterior/próxima, responsável pela
  vistoria, operador do ponto, data, início, conclusão, status, resultado, termo (Liberada/Não liberada — só UBS),
  observações gerais.
- **Resposta por item**: C ou NC, data/hora, observação, fotos, reavaliações (até 3, cada uma com C/NC e data/hora).
- **Não conformidade**: equipamento, item, descrição, observação, fotos, data/hora, quem registrou, plano de ação
  (o que, como, quem, data prevista) e situação (aberta / concluída — só fecha quando alguém autorizado encerrar).
- **Histórico de correções**: depois de enviado, o operador não altera; correção só por administrador, registrando
  quem, quando, o que mudou e o motivo.

Status: Não iniciado · Em andamento · Concluído · Concluído com não conformidades.

### 2.3 Banco de dados

IndexedDB no aparelho (fila offline). A sincronização fica preparada, mas **só liga quando houver banco central**.
Sugestão: Supabase na conta corporativa, como no app de Fotos TSI (a confirmar — D20).
